## 1. 系统概述

任务：无人机在场地上空陆续报出饮料罐坐标，小车逐个把罐子收进收集站。

一轮的完整链条：

```
无人机报出罐子 x/y  →  合成 standoff 位姿  →  几何净空检查  →  LLM 挑下一个动作
   →  导航到 standoff 点  →  纯平移逼近  →  深度识别 + 机械臂抓取
   →  导航到收集站  →  放置  →  回写任务记忆  →  下一轮
```

关键设计取向有三条，后面各章展开：

1. **导航只负责粗定位，精度由到达后的闭环补**。导航到点误差约 ±0.10 m，抓取要求的捕获窗口只有约 23 cm × 8 cm，中间这段差距由「纯平移逼近环」填平，而不是靠把导航调准。
2. **安全由确定性几何层保证，不由 LLM 保证**。会撞的候选在进入 LLM 的 enum 之前就被删掉，LLM 挑错顶多路径不优。
3. **罐子在传感器里是不存在的**。罐高 12 cm，在雷达平面以下，costmap 里没有它们，所以「会不会撞罐」必须离线算，撞了也不会有人报警。

真机最好成绩：五罐闭环 5/5 零干预，6 分 12 秒（2026-08-08 夜）。多次复现 5/5，含一趟按无人机发现顺序动态规划的。

## 3. 分层架构

```
┌──────────────────────────────────────────────────────┐
│  本机 · code/planning/          只依赖 PyYAML         │  与机器人无关
│  任务记忆 · 几何门 · LLM 决策 · 离线仿真               │  不需要 ROS
└─────────────────────┬────────────────────────────────┘
                      │  ssh + argv + 退出码            ← 移植边界
┌─────────────────────┴────────────────────────────────┐
│  run_one_can.sh <can> <color> <station>              │  换机器人只需重写这一层
├──────────────────────────────────────────────────────┤
│  车上 · code/grasp/ + code/car/                       │  JetRover 专有
│  nav_goto → approach → final_track_and_grab_y0       │
└──────────────────────────────────────────────────────┘
```

计算放在本机的原因：8B 模型跑在车上带不动。本机通过 ssh 驱动车，沿用早期 `car_run.py` / `bottle_run.py` 已验证的架构。

### 3.1 数据流

| 环节 | 载体 | 说明 |
|---|---|---|
| 无人机 → 任务记忆 | `~/drone_feed.jsonl` | 逐条追加，带 `reveal_at`，主循环按时间捞新罐子 |

## 4. 定位与建图

### 4.1 现状：hector scan-matching，无里程计

建图与定位都由 `hector_mapping` 承担，没有轮式里程计做先验。这带来两条硬约束：

- **地图不持久化**。车一重启地图清零，坐标系原点＝开机时车的位姿，旧航点在新图上是乱坐标。
- **纯旋转会漂**。2026-07-23 实测：纯旋转指令下位置估计滑了 0.42 m，move_base 追着鬼影不收敛。逼近环全程 `angular.z = 0` 就是为了绕开这条。

### 4.2 「炸图」：当前最主要的失败模式

症状：位姿估计突然跳变，地图被写坏，之后一切导航目标都指向错误位置。

**视觉判据**：rviz 里未知区被扇形条纹啃掉（错误位姿下自由空间射线的痕迹）。

**已定性的病因（两种，均为现场实证）**：

| 场景 | 病因 | 处置 |
|---|---|---|
| 室内电梯厅（08-27） | 场景里有会整体改变几何的东西——用户当场看到有人开电梯门 | 摆场地时把电梯门、自动门当禁区 |
| 室外空旷（08-29） | 根本没有特征，scan-match 没东西可咬 | 把空旷那面挡起来加特征，当场见效 |

**已被证伪的两条猜想**（别再花时间）：

- 「TEB 转太快（`max_vel_theta=0.25`）」：08-27 下午用 teleop 以 0.10 rad/s 遥控照样炸。
- 「卡住时反复原地转把图转坏了」：08-15 与 08-29 两次查 bag，`skip pre-rotate` 分支实际使 re-rotate 从未触发，卡住那段 `cmd_vel` 全零、车没动。

**一条推测，尚未验证**：`nav_hector_bfc.launch` 里 `map_update_angle_thresh=0.06 rad`（3.4°），上游默认是 0.9 rad（51°）；`map_update_distance_thresh=0.1`（默认 0.4）；`map_multi_res_levels=2`（默认 3）。每走 10 cm 或每转 3.4° 就把当前扫描重写进地图，位姿一有误差就立刻固化，下一帧再拿被污染的地图匹配，构成正反馈。**验法**：同场地同样走一圈，比 `align_check.py` 的「10 cm 内百分比」，08-29 两张图的基线是 97% 和 93%。改回上游默认值约 2 分钟，已有备份。

### 4.3 漂移的在线仪表

验「有没有漂」必须用 **scan-to-map 对齐**（`align_check.py`，只读，不动车），不要比对两张占据栅格——08-15 用错仪表得出过「图没炸」的错误结论。

| 状态 | 中位对齐误差 | 10 cm 内占比 |
|---|---|---|
| 健康 | 0.000 m | 94% ~ 99% |
| 已漂 | 0.335 m | 5% |

判据：**中位 > 0.05 m 就停**。腿与腿之间插一次体检，成本很低。

另一个便宜的早期警报：抓取侧的 `measure miss` 次数与逼近耗时。健康的一趟全程 miss 为 0；08-04 那次地图退化是 0 → 0 → 9 → 18，第三腿就崩了。

### 4.4 IMU 与 EKF 的实际状态

IMU 传感器本身是好的（加速度模长 9.82 = 重力），但固件不做姿态融合，陀螺零偏约 0.01 rad/s（0.7°/s），裸积分 1 分钟漂 42°，因此必须每次现测零偏（`imu_debias.py`）——零偏还会温漂，15 分钟变 15%，硬编码不行。

**一条被修正的旧结论**：「上 IMU + EKF 是根治」说过头了。`nav_hector_ekf.launch` 里唯一对症的开关实测反而更差：

| 设置 | 真实转角 | hector 报的角 | 误差 |
|---|---|---|---|
| `use_odom_prior=true` | +24.06° | +13.31° | 10.7° |
| `use_odom_prior=false` | +25.13° | +25.45° | 0.32° |

那套 EKF 治的是「朝向估计抖导致车一扭一扭」，而那个病 07-28 换 TEB + 麦轮横移已经解决。它现在的形态治不了 scan-match 失配。

⚠️ `nav_hector_ekf.launch` 默认 `use_teb=false`，直接用会退回 DWA，丢掉 TEB + 麦轮横移。

## 5. 导航

### 5.1 规划器：TEB + 麦轮横移（现行）

07-28 从 DWA 换到 TEB，同时放开侧向运动约束。关键在于 `weight_kinematics_nh` 这一个参数：默认值 1000 会重罚一切侧向运动，实测 TEB 全程 `vy` 恒为 0.0000，等于全向底盘白装。

`nav_teb_holo.launch` 的现行值：

```
max_vel_x: 0.15      max_vel_y: 0.10      max_vel_theta: 0.25
acc_lim_y: 0.5       weight_kinematics_nh: 1.0      yaw_goal_tolerance: 3.14
```

这个 launch 只覆盖上面六项，其余沿用仓库里的 TEB 参数文件——其中 `xy_goal_tolerance: 0.08` 会直接影响放置精度（见 7.5）。

⚠️ 权重调低不等于它一定会用横移。跑完看 `obstacle_check.py` 报的 `vy 均值` 才算数。

换规划器的实测收益（同场地同目标对照，`obstacle_check.py`）：扭动 −89%、单腿耗时快 5 倍、大掉头时的朝向变号 0 次、绕障 43 s → 10 s；DWA 摆死的侧面贴障工况，TEB 9.3 s 脱困。

`yaw_goal_tolerance` 保持 3.14（即完全放弃到点朝向），这是有意的：**车的朝向根本不需要对**，抓取只关心罐子在臂基座系里的位置。收紧它会逼出大角度原地旋转，直接触发 4.1 那条漂移。

### 5.2 `nav_goto.py`：rotate-then-go

导航封装成「先原地转到目标方向，再走过去」。原地转由 `rotate_to.py` 用 TF 反馈完成，破的是 DWA 大掉头陷局部最优的病根。

⚠️ `rotate_to.py:22` 的角度容差是写死的 7°，是后面落点误差的成因之一（见 7.4）。

### 5.3 TF 原点

`base_footprint` 曾被定义在雷达上，比旋转中心靠前 0.10 m。07-28 之前所谓「每转一次漂 0.2 m」大半是这个几何偏置，不是标定问题，TF 已修。

配套结论：**不存在「每米歪多少」这回事，不要去标定电机**（`straight_scaling.py` 的实测结论）。

### 5.4 实测速度与时序

| 项 | 实测值 |
|---|---|
| TEB 标称行进速度 | 0.144 m/s |
| 从敲下发车命令到车真的动 | ≈ 31 s |
| 导航到点误差 | 0.08 ~ 0.11 m |

31 s 这个数的用处：录像时外部机位不用卡点。

## 6. 逼近环（`approach.py`）

### 6.1 为什么是纯平移

导航交付 ±0.10 m 且朝向不受约束，抓取要求罐子落在约 23 cm × 8 cm 的捕获窗口内。中间这段由到达 standoff 点之后的闭环补齐，控制量只用麦轮平移：

- 罐子 x 偏大 → 车往前（`linear.x > 0`）；罐子 y 偏左 → 车往左（`linear.y > 0`）；`angular.z` 全程为 0。
- 不转车 ⇒ 不触发 hector 旋转漂移。这是这个设计的全部理由。

07-23 建成当天曾提出的 pre 点、共线三点、servo1 扫视三种方案**都是多余的**，实测不需要。

### 6.2 参数（命令行默认值）

| 参数 | 默认 | 含义 |
|---|---|---|
| `--target` | 0.35 | 目标距离（m） |
| `--key` | `dist` | 收敛用哪个量。⚠️ 录 standoff 点必须用真跑同一套参数 `--key x --target 0.35`，与默认 `dist` 差 2.9 cm |
| `--tol-x` / `--tol-y` | 0.015 | 收敛容差 |
| `--min-dist` | 0.32 | 再近就不许往前 |
| `--gain` | 0.7 | 比例增益 |
| `--first-step` | 0.03 | 第一步限得很小，用于带符号自检 |
| `--max-step` | 0.12 | 单步位移上限 |
| `--budget` | 0.60 | 总位移上限（安全阀） |
| `--max-iter` | 8 | 最大迭代次数 |
| `--speed` | 0.06 | 平移速度（m/s） |

「同向假设」（罐子 y 偏大 ⇒ 车往左）没有被独立实测验证过，所以第一步限小并带符号自检：动完之后若误差反而朝反方向跑，立刻停下报错，不会一路跑飞。

### 6.3 已知短板

- `--search-step 0.06` / `--search-max 0.12` 的搜索预算很小。罐子被人踢移之后**补不回来**（08-27 实测），只能人手摆正。
- `measure` 服务的 8 s 超时在搜索阶段是纯浪费，已知未改。

## 7. 抓取与放置

### 7.1 链条

```
LAB 颜色阈值分割 → 取轮廓质心 → 该像素深度反投影出 3D
   → 手眼外参（eye-in-hand）→ 进程内 IK → 预抓取 → 下探 → 合爪 → 抬升 → 送站 → 张爪
```

两条实现细节值得单独记：

- **IK 走进程内直调，不用厂商的 `/kinematics/set_pose_target` 服务**——那个服务对一切目标（含厂商自测点）都无解。进程内 `get_ik` + `set_link` + `set_joint_range` 完全正常。
- **深度不能取罐心**。金属罐正中心是镜面，深度全无效。取深度要按检测半径逐步放大窗口取中位数（半径系数 0.3 / 0.5 / 0.7，≥20 个有效点才取）。

### 7.2 甜点区与工作边界

| 距离（臂基座前方） | 结果 |
|---|---|
| < 0.31 m | 伸臂撞翻罐子 |
| 0.33 ~ 0.38 m | 稳抓 |
| > 0.40 m | 够不到 |

抓取高度被 `target[2] = grasp_height` 无条件覆盖成固定的 0.12 m。

手眼标定有 13.4° 倾斜未修。抓取忍得了是因为逼近环是闭环，能吸收 0.35 m 处约 8 cm 的误差；这也是深度点云暂时不能拿去做导航避障的原因（见 12.2）。

### 7.3 判成败：夹爪回读

夹爪位置语义：0 = 全开，420 = 全合。实测：张开 ≈ 63 / 夹住易拉罐 ≈ 250 / 空夹 ≈ 418。

⚠️ **「夹住」是一个区间，不是单边阈值**——张开时读数同样小于 350。`grip_empty_thresh = 350` 只用于判空夹。

历次成功抓取的夹爪读数集中在 236 ~ 261，与空夹的 404 ~ 418 之间没有重叠。

### 7.4 `detected z` 是相机位姿的仪表

抓取节点日志里的 `grasp height: detected z=...` 这个值会被固定高度覆盖掉，**它不是病因，是仪表**——它读的是「相机认为罐子有多高」。罐子实际高度是常数，所以 z 读错只说明一件事：相机位姿与软件假设的外参不一致。而 x 和 z 出自同一条射线与同一套假设外参，**z 偏低是看得见的症状，x 偏了多少是看不见的，爪子正是照着那个 x 伸出去的**。

| | `detected z` | 结果 |
|---|---|---|
| 失败 5 次 | 0.064 ~ 0.075 | 418 空夹 |
| 成功 4 次 | 0.087 ~ 0.117 | 251 / 251 / 253 / 254 |

九次零重叠，健康值逼近固定抓取高度 0.120。

⚠️ `measure` 服务返回的 z 与这个差一个固定量（同期：病态 0.094 ~ 0.106 / 健康 0.145），**两个判据别混用**。

用法：开工起完抓取侧，`set_color` 后 `measure` 看一眼 z，5 秒判断要不要动手。前提是**臂真的在观察姿势**——不在位时读到的 z 是废数。

⚠️ 单次读数不能判死相机。同一罐同一位置连抓两次一败一成、`detected z` 在 0.123 → 0.079 之间帧间跳 4.4 cm 的情况出现过（罐子上半截裸铝反光让检测框一上一下）。**要连测看稳不稳；失败一次先原样再试，连败两次才停。**

### 7.5 放置：落点误差是结构性的

三场 15 次送站的落点误差（换算到「罐子落点相对箱心」）：最小 6.1 / 中位 10.1 / 最大 12.9 cm，**没有一次是准的**。08-08 那次罐子掉在箱外，11.7 cm 只排第 3，12.9 和 12.2 那两次反而成功了——它不是离群点，是**整个分布贴着悬崖边**。

真正的杀手是纵向：15 次里 13 次偏近，失败那次 −11.4 cm 是绝对值最大，第二名 −10.9 cm，**只差 5 毫米**。

两个误差源都钉到了具体参数：

1. **纵向系统性偏近约 10 cm** = TEB `xy_goal_tolerance: 0.08` + 车总是从远处接近，一进容差圈就刹。15 次到点距离 0.07 ~ 0.12 m，没有一次好过 7 cm。
2. **朝向残差 7°** = `rotate_to.py:22` 写死 `tol = math.radians(7)`。日志呈双峰：不用转的 6 次停在 0.3 ~ 1.8°，需要转的 9 次全卡在 6.1 ~ 7.0°（刚跨阈值就退出）。7° × 0.40 m 力臂 = 4.9 cm 横偏，与实测 4.6 ~ 4.9 cm 逐条吻合。
3. **放大器**：`place` 纯开环固定伸手（`place_pose=[0.32,0,0.13]`），返回的 `success: True` **只代表爪子张开了**，不代表罐子进了箱——系统从头到尾不知道自己失败了。

修法按性价比排（都还没做）：① 零成本：录 collect 点时车往箱子方向多停约 10 cm 抵消偏置，反正每次断电都要重录点；② 一行：`rotate_to.py` 的 tol 从 7° 改到 3°，砍掉约 3 cm 横偏；③ 物理：箱子换大或摆正。⚠️ 不建议轻易收紧 TEB 的 `yaw_goal_tolerance`（现 3.14），那更根本但从没实测过。

⚠️ 08-09 起容器换成了透明塑料箱（此前是白色泡沫箱），箱壁高且直，落在边缘更容易弹出。

## 8. 安全层：几何门

### 8.1 为什么必须有

罐子只有 12 cm 高、直径 66 mm，在雷达平面以下，**costmap 里根本不存在**。「这条腿会不会从别的罐子旁边压过去」只能自己算，撞了也不会有任何报警。

### 8.2 标定常数与阈值

```
CAN_AHEAD = 0.45   # 罐子 = standoff + 0.45 m × [cos yaw, sin yaw]
ROBOT_R   = 0.16   # 车体半径
CAN_R     = 0.033  # 罐子半径（Ø66 mm）
HARD      = 0.193  # 必撞线 = ROBOT_R + CAN_R
WARN      = 0.50   # 低于此不进 LLM 的 enum
SELF_MIN  = 0.30   # 去程离目标罐自己最近不得小于此
```

`CAN_AHEAD = 0.45` 不是量出来的，是标定出来的：逼近环收敛到臂基座 x = 0.35 之后再 `--nudge -0.08` 录点，07-29 两次 5/5 把这个几何关系钉死。**反过来用就是从罐子坐标合成 standoff 位姿**——所以无人机只报 x/y 就够了，yaw 不是罐子的属性（录点录的 yaw 是「我打算从哪边开过去」）。

`SELF_MIN` 是 08-01 的教训：standoff 若落在罐子的另一侧，去程会从罐子身上正面压过去，实测净空 0.039 m。

### 8.3 净空怎么算：问真实路径，不要用直线

`plan_clearance.py` 向 `/move_base/make_plan` 要 Navfn 算出的实际折线，逐段量点到线段距离。

直线近似差多少（450 个配对样本）：

| 指标 | 值 |
|---|---|
| 高估比例 | 56% |
| P90 误差 | +0.18 m |
| 最大误差 | +0.35 m |
| 「直线说安全、真实路径进告警区」的腿 | 12 条 |

单看极端个例更直观：同一条 `collect_a ↔ can3` 腿，直线模型说 0.73 m 安全，`make_plan` 的真实路径只有 0.17 m，差 0.56 m——照直线跑，这条腿会直接撞上 can4。08-01 还有一条直线净空 0.48 m 判「安全」的腿，车实际把罐子撞倒了。

⇒ **`--real-clearance` 不是可选项。** 真跑时它默认就开，`--dry-run` 才需要显式加。

⚠️ **离线仿真（`mission_sim.py` / `plan_next.py --no-llm`）至今仍用直线模型**，所以离线结果不能当真机安全的证据。若只用直线，告警线得抬到 0.82 m 才等效。

### 8.4 告警线 0.50 的正当性

`make_plan` 给的是全局路径，TEB 执行时还有自己的偏差，两者互补：

| 工况 | TEB 实际轨迹偏离全局路径 |
|---|---|
| 空旷路径（1140 个采样） | 中位 0.024 / P90 0.070 / P99 0.126 / 最大 0.166 m |
| 主动绕障 | 可达 0.48 m |

0.50 是照后者定的。用 08-29 那条实测紧腿验算：净空 0.253 m，扣掉 0.166 m 的轨迹偏离只剩 0.087 m，**低于 0.193 m 的必撞线**——这条腿真跑很可能撞。这是安全层有价值最硬的一段证据。

⚠️ 做这类分析必须按 mission 日志里每条腿的 `[起始 epoch → GRAB success epoch]` 精确切时间段。不切导航窗口，逼近阶段车由 `approach.py` 直发 `/cmd_vel`、根本不跟全局路径，会算出最大 3.262 m 的假数；不切「罐子还站着」的时段，会算出 0.032 m 的假「必撞」。

## 9. 任务规划与 LLM 决策

### 9.1 分层安全边界

```
确定性层（plan_next.py 上半）        LLM 层              执行层（车上，已验证）
坐标 → map 系                       只在**通过几何门     run_one_can.sh:
合成 standoff 位姿          ──►     的**候选里挑一个  ──► 导航→逼近→抓→送站→放
几何净空检查（seg_pt_dist）         {reason, next}         + 夹爪回读
```

**LLM 挑错顶多路径不优，撞不了罐子——会撞的选项压根没进 enum。** 这条边界的依据是两次实测：`enum` 只保证格式和词汇合法、不保证语义（07-01：问不存在的地点，模型会硬塞一个合法答案）；`temperature=0` 不保证确定性（07-08：同一 prompt 干跑与真跑排序不同）。

模型：本地 Ollama 跑 qwen3:8b，没有云服务、没有 API key。

### 9.2 三种模式

| 模式 | 含义 | 有没有优化空间 |
|---|---|---|
| `single` | 单收集站 | **没有**。总路程 = 2 × Σ\|站 − 罐\|，与顺序无关，数学上恒为 0 |
| `free` | 双站自由选 | 有。选站决定下一条腿从哪起步，顺序与选站耦合 |
| `sorted` | 双站按颜色分类 | 有限。站由颜色定死，只有顺序自由；颜色分布偏（如四红一绿）时退化 |

双站还白捡一条：总路程反而短 11% ~ 23%（实测 25.64 m → 19.75 / 22.72 m），而电量是硬约束。

### 9.3 唯一能安全打断的阶段

| 阶段 | 能打断 | 理由 |
|---|---|---|
| 去 canN 导航 | ✅ | actionlib cancel 现成；**手是空的，没有状态要收拾** |
| 逼近 approach | ❌ | 打断会把车丢在「看不见罐子」的随机位置 |
| 抓取 grab | ⛔ | 臂在动、爪在合。失败路径不收臂，臂伸着下次导航会拿它撞东西 |
| 夹着罐子回站 | ❌ | 手是满的，改道做不了任何事 |
| place | ⛔ | 同 grab |

⇒ LLM 随时可触发、随时给决策，但**只有「空手去接罐子」那段导航会真改道**；其他阶段记下来，走完当前罐子立刻重规划（`--interruptible`，nav 期间每 2 秒捞一次 feed）。

⚠️ 「车走到哪了」是按标称速度 0.144 m/s 估的，不查 TF。这个数只喂给「还剩多远 vs 改道白走多远」的粗判断，不参与任何控制。

### 9.4 必须诚实的一条：当前 LLM 输出等于在线贪心

在 08-08 的真实布局上（五罐两站，净空来自真机 `make_plan`），连跑 4 次输出完全一致：

| | 路程 | 顺序 |
|---|---|---|
| 离线最优（上帝视角，理论下界） | **16.08 m** | can5:A→can2:A→can1:B→can3:B→can4:B |
| 在线贪心（最简基线） | 16.74 m | can5:A→can1:A→can2:A→can4:B→can3:B |
| qwen3:8b | **16.74 m** | **与贪心逐字相同** |

理由字段自己招了：「can5 的 trip 最小」「can4 的 trip 更短（4.39 vs 4.58）」。**病根不在模型笨，在 system prompt 的通用判据里写着「trip 小的优先」**——贪心策略是我们自己写进去的。

两个推论：

1. 想要非贪心行为只有两条路，必须选一条：① prompt 里不给贪心规则，改成给「还剩哪些罐子 + 各自到两个站的账」让它自己权衡（风险：小模型不会把数字组合成权衡，08-01 已验证过这个缺陷）；② 承认这层就是贪心，把卖点换成物理 Verifier 或流式部分信息下的鲁棒性。
2. 既然输出等于贪心，**真机跑 LLM 版拍出来和写死顺序版没有区别**（同样五条腿，只多走 0.66 m），为录像去跑 LLM 版收益为零。

还有一条与场地设计有关：随手摆的布局里，贪心恰好等于最优的占 61%，亏超过 10% 的只占 2%。要让顺序优化显出价值，必须照模式设计场地——**同色罐子空间上分散、红绿交错摆、两个站放对角**。

## 10. 标准作业流程

### 10.1 开工

```bash
bash ~/jetrover_up.sh              # 默认红罐做抓取体检
COLOR=green bash ~/jetrover_up.sh
```

七步，每步带判据、不过就停，**全程不会让车移动**：连车 → 抓取栈 → `cmd_vel` 桥接 → 抓取只读体检 → 雷达 → 导航栈 → 清旧航点 → 弹窗。

两个容易漏的点已经固化进脚本：

- `start_final_grab.sh` **不含** `cmd_vel_to_motor`，少了它逼近环的平移指令全打空。
- 录点前必须先备份再清空 `llm_nav_places.yaml`。旧图残留点会让漏录的那个静默导航到乱坐标；清空才能「失败得响」。

### 10.2 建图与录点

```bash
bash ~/pop_standoff.sh   # 一个窗口：tel 遥控建图 + 开到跟前敲 can1..canN / collect 录点
```

- 建图与录点在同一个终端完成。⚠️ 脚本里车 IP 写死，DHCP 变了要先改。
- `~/.standoff_rc` 里 `export N_CANS=6` 控制罐子数量；改完文件后，已经开着的那个窗口必须 `source ~/.standoff_rc` 才生效。
- 摆好罐子后先 `capture_one.py` 验一次检测：**「录点成功」≠「抓得住」**。光线差时色块会碎成 4 块、框心偏离轴心，必然空夹。
- standoff 点离墙 < 0.35 m 必须换摆位（`standoff_wall_check.py` 量）。**重试机制救不回来**：`pick_yaw` 的重试只优化「离别的罐子远」，完全不看墙。

### 10.3 发车前

```bash
python3 ~/clearance_scan.py --state <state>        # 全布局净空扫描
python3 ~/mission_run.py --state <state 的副本> --dry-run --real-clearance
python3 ~/mission_run.py --state <state> --order "can5,can4,..." --record <tag>
```

⚠️ `--dry-run` **会把 state 写脏**（罐子被标成已收），必须用副本跑，真跑前恢复全 pending。

⚠️ `--order` 有两个已知行为差异：写 `canN:station` 会**绕过几何门**（系统先拿自己选的站过门，过门后才用你指定的站覆盖）；遇到过不了几何门的罐子会**整个任务停车，不会跳过去拿下一个**。

### 10.4 跑起来之后

**跑起来就不要主动停**。分工是用户 08-27 定的：炸图由人看 rviz 喊停，程序自己该重试的让它重试。

08-27 第五趟第 5 腿 `gripper=404` 空夹，没有干预，`mission_run` 自己重试，第二次 247 抓住——**手贱去停就是 4/5**。

杀进程要用 `pgrep -f "^python3 -u $HOME/mission_run.py"` 精确取 PID，且只能发 SIGINT：SIGTERM 不触发 `except BaseException`，录像收不了尾。

### 10.5 复盘

逐腿的账（耗时、逼近步数、miss、夹爪读数、到点误差）直接从运行日志正则提。

⚠️ `mission_review.py` 对「写死顺序」这条路是瞎的：它的路程对照和决策逐条只读 LLM 决策日志，走 `--order` 时全程不调 LLM ⇒ 没有日志 ⇒ 它会报「只收了 0/5」。

⚠️ 抓取侧一出异常，第一件事是 `cp` 走 `/tmp/final_track_and_grab.log`——那是 tmpfs，关机就没了。这个错犯过两次。

## 11. 已知失败模式与处置

| 现象 | 判据 | 处置 |
|---|---|---|
| **炸图** | rviz 未知区被扇形条纹啃掉；`align_check` 中位 > 0.05 m | 停车。场地加特征、把会动的门当禁区。见 4.2 |
| **雷达从 USB 掉线** | `/scan` 静默，但节点活着、`rosnode ping` 正常 ⇒ **先看 `/dev/ttyUSB0` 这个文件在不在** | 物理断电重启。只重启节点无效。端口号会变（USB0→USB2），但 `start_lidar.sh` 用 by-id 会跟上，端口名不是病根 |
| **雷达本体死没死** | 串口探针：`serial.Serial(port,115200)` → 写 `A5 50` → 收到 `a55a1400000004...` = 活着 | 只读诊断，能把「雷达坏了」和「ROS 侧问题」干净分开 |
| **雷达起早了** | 掉电重启后 USB 是拨开关那一刻才枚举出来，起早了 tmux 会话是空的 | 拨完开关再起 `start_lidar.sh` |
| **行驶中硬掉电** | ssh `Connection closed by remote host`，之后全 `Connection refused`；`last -x` 会话以 `crash` 结尾 | 两个独立成因：① 蹭墙导致线缆接触不良（已修过、多次复发，动车前先按住那条线晃一晃复现）；② 非满电起跑。**铁律：非满电不开建图**（建图和录点同时进行，一次掉电把图和点一起赔光） |
| **夜间 / 户外抓不到** | 罐身 LAB 的 a 通道与地板完全重叠（125~130 vs 129~130）⇒ 调阈值救不了 | 车载手电筒补光，实测检测框 20×22 → 58×106，当场恢复 |
| **`set_color` 敲错颜色** | 症状是「录点识别不到」 | 那不是拒绝，是把抓取节点整个搞崩了，要重起 |
| **空夹一次** | `gripper ≥ 350` | **先原样再抓一次**，连败两次才停。见 7.4 |
| **罐子被人踢移** | 逼近环搜索失败 | 搜索预算 0.06/0.12 补不回来，人手摆正 |
| **录像是不是完整** | 三个信号：有 `meta.json` / bag 自己从 `.active` 改名 / mp4 有 `moov` | 掉电截断的 mp4 可用 `fix_truncated_mp4.py` 修（实测 10333 帧全回来），bag 用 `rosbag reindex` |

## 12. 局限与下一步

### 12.1 建图定位：换成「静态地图 + AMCL」（零件齐全，尚未动手）

建图仍用 hector → `map_saver` 存图 → 发车前换 `map_server`（只读地图）+ `amcl`（定位），odom→base 由 IMU + EKF 提供。

**AMCL 永远不写地图 ⇒「污染地图 → 匹配更差 → 更污染」这个环在原理上被切断。** 白捡的好处：航点跨重启可复用，省掉每次重录点约 15 分钟。

车上零件全在：`amcl` / `map_server` / `map_saver` / `robot_localization` / `cmd_odom.py` / `imu_debias.py`。风险：这台车没跑过 AMCL，要现场调运动模型噪声（`cmd_odom` 是开环，噪声要给大）并给初始位姿，**至少占一趟**。

另一条独立的便宜保险：**陀螺当炸图探测器**——比 hector 的 yaw 变化率与 IMU 陀螺 z，持续背离就立刻停车。08-29 两趟都是「炸了之后车还在跑」才从少收一个罐变成 2/6。

### 12.2 深度点云进 costmap：先修手眼标定

「矮障碍看不见」这个结构性缺口的正解是让深度点云进 `local_costmap`，但前置条件是先修 13.4° 的手眼倾斜，不是能顺手加的东西。三条比量程更硬的约束：

1. 视场 83.5° 只覆盖前方，而这套栈大量用麦轮横移，横着走时侧面全盲；
2. 相机装在臂上、朝向随臂变，导航姿势与抓取姿势打架；
3. 手眼误差按距离线性放大：0.35 m → 8 cm（闭环能吸收）/ 1.5 m → 36 cm。罐子本身才 6.6 cm 粗，**障碍位置偏 36 cm 的 costmap 比没有还危险**（在错的地方画禁区，真障碍漏在外面）。

短期仍走「场地几何隔离 + 跑前几何门」。

⚠️ 顺带澄清一个流传的误会：深度相机「只能看 0.3 ~ 0.9 m」不是量程，那是 `record_cam.py` 深度伪彩视频的配色区间。真正限制探测距离的是臂的观察姿势（光轴俯角约 49°，视野被车前 0.07 ~ 0.67 m 的地面填满）。

### 12.3 放置精度

7.5 的三条成因都还没修。落点误差中位 10.1 cm，离「掉在箱外」只差 5 mm 的余量。

### 12.4 LLM 层的定位

见 9.4：要么改 prompt 让它真的做权衡，要么把卖点换成物理 Verifier / 流式鲁棒性。三条可测的对照线是**离线最优 / 在线贪心 / 在线 LLM**，在线永远赢不了离线，那个差距就是「不知道未来的代价」。

## 14. 术语

| 术语 | 含义 |
|---|---|
| standoff 点 | 罐子前方 0.45 m 的导航目标点，不是抓取位置 |
| 逼近环 | 到达 standoff 点后用纯平移把罐子送进抓取甜点区的闭环 |
| 甜点区 | 臂基座前方 0.33 ~ 0.38 m，抓取稳定的距离区间 |
| 几何门 | 发车前算「这条腿会不会从别的罐子旁边压过去」的确定性检查 |
| 净空 | 路径到某个罐心的最近距离 |
| 必撞线 / 告警线 | 0.193 m / 0.50 m |
| 炸图 | hector scan-match 失配导致位姿跳变、地图被写坏 |
| 空夹 | 爪子合拢但里面没有东西，夹爪回读 ≥ 350 |
| 送站 | 把罐子送到收集站并放下 |
